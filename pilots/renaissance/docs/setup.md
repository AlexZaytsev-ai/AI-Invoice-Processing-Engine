# Настройка демонстрации

Цель: повторить путь PDF → проверки → PostgreSQL → решение в Telegram → реестр Google Sheets на вымышленных данных.

## 1. Отдельная база

Подготовьте PostgreSQL и выполните в отдельной демонстрационной базе:

```bash
psql "$DEMO_DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/01-schema.sql
psql "$DEMO_DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/02-demo-data.sql
```

Схема `renaissance` восстановлена по полям и SQL трёх экспортов. Это не дамп исходной базы и не миграция существующих таблиц. Скрипт `01-schema.sql` не дополняет уже созданные таблицы: для воспроизводимой демонстрации нужна новая база. SQL-скрипты не выполнялись на рабочей базе пользователя.

В `invoices` по умолчанию заданы `version = 1` и `approval_status = pending`. Нода создания рассчитывает на эти значения. ИНН и банковские счета хранятся как текст, суммы — `numeric(18, 2)`.

Демонстрационный поставщик: `ДЕМО ПОСТАВЩИК`, ИНН `0000000001`, расчётный счёт `00000000000000000001`. Эти реквизиты вымышлены. Не добавляйте поставщика `0000000002` до теста неизвестного поставщика.

## 2. Импорт workflow

Через меню n8n **Import from File** импортируйте:

1. `workflows/invoice-intake.json`
2. `workflows/invoice-approvals.json`
3. `workflows/invoice-report.json`

Все три файла имеют `active: false` и пустой `pinData`. Имена нод сохранены: выражения обращаются к ним по имени.

JSON сохраняют версии нод из предоставленных экспортов. Общая версия n8n неизвестна. После импорта убедитесь, что ноды доступны и параметры отображаются корректно. Локальный импорт в n8n этого пакета не выполнялся.

## 3. Подключения и значения

| Что настроить | Где |
| --- | --- |
| Gmail OAuth2 | Gmail Trigger и Get Invoice Email в приёме |
| OpenAI | «Проанализировать инвойс»; в исходном экспортe выбран `gpt-5-mini` и JSON Schema |
| PostgreSQL | Все PostgreSQL-ноды трёх workflow |
| Один Telegram-бот | Все отправки в приёме и все Telegram-ноды решений |
| Telegram Chat ID | Заменить `YOUR_TELEGRAM_CHAT_ID` в отправках и в коде Parse Approval |
| Telegram User ID | Заменить `YOUR_TELEGRAM_USER_ID` в коде Parse Approval |
| Google Sheets account | Sync Report |
| ID Google-таблицы | Заменить `YOUR_GOOGLE_SHEETS_DOCUMENT_ID` в Sync Report |

User ID определяет, кто может нажать кнопку. Chat ID определяет разрешённый чат. В личной переписке они обычно совпадают; в группе это разные значения. Со своего аккаунта сначала нажмите Start у бота.

Исходная отдельная нода Add Supplier оставлена без соединений и содержит вымышленные реквизиты. После `02-demo-data.sql` запускать её не требуется.

Источник OpenAI-ответа в Prepare Invoice Data — `output[0].content[0].text`. Проверьте форму ответа вашей версии ноды на одном PDF: все поля должны отображаться как значения, а не `undefined`.

## 4. Google Sheets

Создайте таблицу и вкладку **Счета**. Вставьте в A1 строку из `demo/report-header.tsv`; она содержит только заголовки:

```text
invoice_id invoice_number invoice_date event_name expense_category supplier_name amount currency version approval_status decided_by decided_at updated_at
```

В Sync Report сохраните **Append or Update Row**, **Map Automatically**, совпадение по `invoice_id`. Названия столбцов должны совпадать с названиями полей SQL. Не создавайте строк с пустым ID.

В исходном экспортe Manual Trigger отчёта выключен. Для ручного запуска временно включите только **Report Start**. Расписание остаётся каждые 15 минут.

## 5. Письмо и обработка

Приём настроен на Gmail-запрос:

```text
in:inbox subject:REN-DEMO has:attachment filename:pdf
```

Отправляйте по одному PDF из `demo/` с темой `REN-DEMO`. После запуска тестового прослушивания отправьте новое письмо: старое письмо не является доказательством работы нового события.

Извлечение настроено на `attachment_0`. Проверьте на входе Extract from File, что это именно PDF. Для сканов распознавание изображения в пакет не добавлено.

## 6. Telegram и связь workflow

Приём счёта отправляет сообщение через бот. Workflow решений получает `callback_query` того же бота. Прямого вызова другого workflow здесь нет.

Кнопка содержит `ren:approve:ID:VERSION` или `ren:reject:ID:VERSION`. `ren` — метка формата, не имя workflow и не URL. Выбор получателя нажатия определяется Telegram webhook, настроенным Telegram Trigger.

На одного бота используйте один принимающий Telegram Trigger. Одновременное тестовое прослушивание и опубликованный Trigger могут заменить webhook друг друга. Для постоянного стенда используйте отдельного тестового бота во всех Telegram-нодах пилота.

Workflow решений должен быть опубликован либо слушать тестовое событие **до** нажатия. Приём запускайте после готовности workflow решений. Отчёт публикуйте, если хотите обновление по расписанию.

## 7. Минимальный прогон

1. `01-new.pdf` → новый счёт `DEMO-3676`, версия 1, `pending`. Кнопки пока не нажимайте.
2. Повторите `01-new.pdf` → точный дубль, обновления и нового сообщения нет.
3. `02-updated.pdf` → сумма 11 000 ₽, версия 2, `pending`.
4. Нажмите кнопку версии 1 → `valid = true`, `applied = false`.
5. Согласуйте версию 2 → `approved`, сообщение обновилось, кнопки убраны.
6. Запустите отчёт дважды → одна строка по этому `invoice_id`, версия 2 и `approved`.
7. Для проверки отказа повторите `01-new.pdf` → версия 3; нажмите «Отклонить» → `rejected`.
8. `03-bank-mismatch.pdf` → ручная проверка, версия 3 не меняется.
9. `04-unknown-supplier.pdf` → ручная проверка, новой записи нет.

PDF — искусственные примеры, а не документы исходного поставщика. Результаты извлечения зависят от модели; сравните сумму, номер и реквизиты с документом.

## 8. Повторное решение той же версии

Задача: отдельно проверить условие `pending`, сохранив актуальный ID и версию. Старая версия проверяет другое условие.

Создайте временный неопубликованный workflow **Manual Trigger → Telegram / Send Message**. Выберите того же бота и свой Chat ID. Добавьте кнопку с Callback Data `ren:approve:<invoice_id>:3`, где ID берётся из вашей базы. **Не используйте ID 4 из исходного пилота: в новой базе ID будет другим.**

После отказа по версии 3 отправьте это тестовое сообщение и нажмите кнопку. Ожидается `valid = true`, `applied = false`; в базе остаются версия 3 и `rejected`. Временный workflow только отправляет кнопку и не содержит Telegram Trigger или PostgreSQL-ноды.

## 9. Что ещё проверить

С другим Telegram-аккаунтом: нажать кнопку → `valid = false`, Save Approval не запускался, база не изменилась. Не заменяйте эту проверку нажатием старой версии: оно не проверяет права доступа. Отдельно проверить отсутствие обязательных полей, `not_invoice`, ошибки API и одновременные поступления.
