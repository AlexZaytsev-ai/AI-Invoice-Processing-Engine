# AI Invoice Processing Engine

[English version](README.md)

## Веб-демонстрация — быстрый запуск

В репозиторий добавлен автономный интерфейс на **React + TypeScript + Vite**. Он демонстрирует существующие ветки обработки на вымышленных данных; запускать n8n, PostgreSQL или внешние интеграции не нужно.

Требуется **Node.js 24.15+ или 22.22.2+** (проверено на 24.20.0). В корне репозитория выполните:

```powershell
npm.cmd ci
npm.cmd run dev
```

Откройте **http://127.0.0.1:5173/**. На macOS/Linux можно использовать `npm` вместо `npm.cmd`. В Windows вариант `npm.cmd` работает и при ограничении запуска PowerShell-скриптов.

Для проверки с телефона в одной локальной сети используйте **`npm.cmd run dev:lan`** вместо `dev`. Vite слушает порт 5173 на сетевых интерфейсах компьютера и выводит адрес `Network`, например `http://192.168.0.107:5173/`. Откройте этот адрес на телефоне, подключённом к тому же Wi-Fi. IP может измениться при переподключении к сети. Команда не публикует сайт в интернете и не создаёт туннели. Обычный `npm.cmd run dev` по-прежнему доступен только на самом компьютере.

Выберите сценарий и нажмите **«Обработать тестовый счёт»**:

| Сценарий | Что показывает интерфейс |
| --- | --- |
| Корректный счёт | Четыре проверки пройдены, создана тестовая запись версии 1; статус «Обработано». |
| Повторная загрузка | Номер + ИНН совпадают, бизнес-данные не изменены; **0 новых записей, 0 обновлений**, версия 1 сохранена. |
| Изменённый счёт | Сумма 128 400 → 142 800 ₽, НДС 21 400 → 23 800 ₽; обновлена та же запись, версия 1 → 2. |
| Другие реквизиты | Видны счёт из документа и счёт из реестра; статус «Требуется ручная проверка», запись не создана, проверка дублей пропущена. |

Каждый сценарий независим и воспроизводим в любом порядке. Реальные записи не создаются даже в сценарии создания. Показаны состояния ожидания, обработки, отмены, ошибки и результата; интерфейс адаптирован под телефон.

**Загрузка своего PDF:** можно выбрать или перетащить один PDF до 10 МБ. В браузере проверяются размер, тип и сигнатура файла. В деморежиме содержимое не извлекается, файл никуда не отправляется, а выдуманный результат не генерируется. Для реальной обработки необходим отдельно подключённый backend.

```powershell
npm.cmd test          # Сценарии, адаптер, валидация PDF и контракт ответа
npm.cmd run build    # TypeScript + production-сборка в dist/
npm.cmd run preview  # http://127.0.0.1:4173/AI-Invoice-Processing-Engine/
```

### Публикация на GitHub Pages

Адрес демонстрации: **https://alexzaytsev-ai.github.io/AI-Invoice-Processing-Engine/**.

В `.github/workflows/pages.yml` настроены установка по `package-lock.json`, проверка сценариев, сборка и публикация. Push в `main` автоматически обновляет сайт; pull request запускает только проверки и сборку. Повторный запуск доступен через **Actions → Deploy autonomous demo to GitHub Pages → Run workflow**. Источник Pages в **Settings → Pages → Build and deployment** должен быть **GitHub Actions**.

`npm.cmd run build:pages` собирает только автономный деморежим и принудительно отключает backend независимо от локальных `VITE_*`. Vite использует base `/AI-Invoice-Processing-Engine/` для production-сборки; обычный dev и запуск в локальной сети сохраняют корневой адрес `/`. Проверка перед публикацией:

```powershell
npm.cmd test
npm.cmd run build:pages
npm.cmd run preview
```

Публикуется **только `dist/`**. Исходные JSON workflow n8n, документация, `.env`, Git и зависимости в артефакт сайта не входят. Секреты для публикации не нужны: Actions использует временный `GITHUB_TOKEN` и OIDC. В репозитории разрешён только несекретный шаблон `.env.example`; реальные `.env*` исключены через `.gitignore`. Вызовы n8n и внешних интеграций в процессе сборки и публикации не выполняются.

Настройка соответствует [руководству Vite для GitHub Pages](https://vite.dev/guide/static-deploy.html#github-pages) и [документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

Приложение автономно: не использует CDN, внешние шрифты, авторизацию, оплату или аналитику. Существующие workflow не менялись; оба вызова **Sync Invoice to Bitrix24** после создания и обновления сохранены. Frontend не импортирует и не запускает эти workflow. В деморежиме нет запросов в Bitrix24, Gmail, Telegram, n8n или рабочую базу. Согласование счетов в интерфейс не входит.

### Будущее подключение реального n8n

Сейчас ничего подключать не требуется: по умолчанию включён `demo`. Адаптер подготовлен, но сам backend в эту версию не входит.

Для следующего этапа потребуется backend того же origin с `POST /api/invoices/process`, принимающий `multipart/form-data` с полем `file`. Backend должен безопасно передавать документ отдельной HTTP-точке входа n8n, дождаться результата и преобразовать его в проверяемый контракт интерфейса. Существующий Gmail-trigger workflow не является HTTP API и напрямую для этого не подходит. Его исходные файлы и вызовы синхронизации следует сохранить; новое подключение проектировать отдельно и проверять на изолированном окружении.

После реализации и отдельной проверки backend скопируйте `.env.example` в `.env.local`, установите `VITE_API_MODE=backend`, оставьте `VITE_API_BASE_URL=/api` и перезапустите Vite / пересоберите приложение. Маршрут `/api` настраивается на сервере или reverse proxy; встроенного proxy на n8n в репозитории нет. При таком переключении PDF отправляется только после нажатия «Обработать PDF», а тестовые сценарии остаются локальными.

**Не помещайте URL секретного webhook, ключи, OAuth-токены или пароли в frontend и переменные `VITE_*`: они доступны посетителю.** Credentials n8n, доступ к базе и ключи должны находиться только на backend. Прямые внешние URL в адаптере запрещены. Подробнее: [контракт API](docs/api-contract.md).

Отдельного DDL / SQL-файла схемы в исходном репозитории нет. По запросам workflow используются `suppliers` (поиск по `supplier_inn`, подтверждённый `bank_account`) и `invoices` (номер, дата, поставщик, ИНН, сумма, валюта, НДС, счёт, статус, версия, `updated_at`, `bitrix_item_id`). Уникальность определяется парой `supplier_inn + invoice_number`. Это описание наблюдаемых полей, а не миграция рабочей базы.

AI-система обработки входящих PDF-инвойсов, построенная в **n8n**. Workflow извлекает данные из документов, проверяет бизнес-правила, предотвращает повторную обработку, сохраняет инвойсы в PostgreSQL и синхронизирует их с Bitrix24.

## Бизнес-задача

Компании ежедневно получают счета от поставщиков по электронной почте. Ручная обработка занимает время и может привести к появлению дублей или оплате по неполным и неподтверждённым реквизитам.

Workflow автоматизирует обработку инвойсов, проверяет критичные бизнес-условия и направляет сомнительные случаи менеджеру на ручную проверку.

## Архитектура Workflow

```text
Gmail Trigger
      ↓
Извлечение текста из PDF
      ↓
AI-анализ инвойса
      ↓
Подготовка данных
      ↓
Данные инвойса валидны?
├─ Нет → Уведомить менеджера → Stop
└─ Да  → Найти поставщика по ИНН
              ↓
         Поставщик найден?
         ├─ Нет → Уведомить менеджера → Stop
         └─ Да  → Банковский счёт совпадает?
                       ├─ Нет → Уведомить менеджера → Stop
                       └─ Да  → Найти существующий инвойс
                                      ↓
                              Инвойс существует?
                              ├─ Нет → Создать в PostgreSQL
                              └─ Да  → Данные изменились?
                                           ├─ Нет → Stop
                                           └─ Да  → Обновить PostgreSQL
                                                          ↓
                                         Подворкфлоу синхронизации с Bitrix24
                                                          ↓
                                              Уведомление в Telegram
```

## Архитектурные принципы

* AI извлекает и структурирует данные инвойса.
* Бизнес-решения принимаются детерминированной логикой workflow.
* Обязательные данные проверяются до дальнейшей обработки.
* PostgreSQL является основным источником данных о поставщиках и инвойсах.
* Поставщик определяется по ИНН, а не по названию компании.
* Составной бизнес-ключ `supplier_inn + invoice_number` защищает от дублей.
* Существующий инвойс обновляется только при изменении ключевых данных.
* Повторный инвойс без изменений останавливается без лишних обновлений.
* Неполные или подозрительные данные передаются менеджеру на ручную проверку.

## Импорт и настройка

Экспортированные workflow очищены для публичного использования. Credentials, персональные ID и адреса частных сервисов в файлы не включены.

1. Импортировать `bitrix24-sync-subworkflow.json` в n8n.
2. Настроить PostgreSQL и Bitrix24 OAuth2 credentials в подворкфлоу.
3. Заменить `YOUR_BITRIX24_PORTAL` в двух HTTP Request нодах Bitrix24.
4. Импортировать `invoice-processing-workflow.json`.
5. Настроить Gmail, OpenAI, PostgreSQL и Telegram credentials.
6. Заменить `YOUR_TELEGRAM_CHAT_ID` в Telegram-нодах.
7. Выбрать импортированный Bitrix24-подворкфлоу в двух Execute Workflow нодах.
8. Перед активацией проверить сценарии создания, обновления, дубля и ручной проверки.

## Бизнес-правила

* Поля `invoice_number`, `supplier_inn` и `bank_account` должны быть заполнены.
* Значение `amount` должно быть больше нуля.
* Поставщик должен существовать в реестре PostgreSQL.
* Банковский счёт из инвойса должен совпадать с подтверждённым счётом поставщика.
* Дубли определяются по паре `supplier_inn + invoice_number`.
* Существующий инвойс обновляется только при изменении бизнес-данных.
* `bitrix_item_id` хранится в PostgreSQL, чтобы обновлять существующую карточку Bitrix24 вместо создания дубля.
* Сомнительные случаи останавливаются и передаются менеджеру на ручную проверку.

## Проверенные сценарии

* Новый валидный инвойс создаётся в PostgreSQL и Bitrix24.
* Повторный инвойс без изменений не создаёт обновлений и уведомлений.
* Изменённый инвойс обновляется, а версия записи увеличивается.
* Неизвестный поставщик направляется на ручную проверку.
* Несовпадение банковского счёта направляется на ручную проверку.
* Отсутствие обязательных данных направляется на ручную проверку.
* При временной ошибке обновления Bitrix24 выполняется до трёх попыток.
