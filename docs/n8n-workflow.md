# Устройство n8n workflow

[Главный README](../README.md) · [Запуск демоинтерфейса](getting-started.md) · [Будущий API](api-contract.md)

Workflow автоматизирует обработку входящих PDF-счетов: извлекает данные, проверяет бизнес-правила, предотвращает дубли и сохраняет результат в PostgreSQL. Сомнительные случаи останавливаются и передаются менеджеру на ручную проверку.

**Это отдельная часть проекта.** Опубликованный сайт воспроизводит её ключевые ветки на тестовых данных. Сайт не запускает n8n, не обращается к рабочей базе и не вызывает внешние интеграции. Подключённого backend пока нет.

## Порядок обработки

1. **Получение документа:** Gmail Trigger получает письмо с PDF-вложением.
2. **Извлечение:** текст PDF передаётся AI, который возвращает структурированные данные. Бизнес-решения принимает детерминированная логика workflow.
3. **Обязательные данные:** проверяются номер счёта, ИНН, банковский счёт и положительная сумма. При ошибке обработка останавливается с уведомлением менеджера.
4. **Поставщик и реквизиты:** поставщик ищется в PostgreSQL по ИНН; банковский счёт сверяется с подтверждённым. Неизвестный поставщик или несовпадение реквизитов останавливают обработку до поиска дублей.
5. **Поиск счёта:** используется составной ключ `supplier_inn + invoice_number`.
6. **Сохранение:** новый счёт создаётся; повторный без изменений завершает обработку без записи и уведомлений; изменённый обновляет существующую запись и увеличивает её версию.
7. **Синхронизация:** после создания или обновления вызывается подворкфлоу Bitrix24, затем отправляется уведомление в Telegram.

## Бизнес-правила и архитектура

- Поля `invoice_number`, `supplier_inn` и `bank_account` должны быть заполнены; `amount` — больше нуля.
- Поставщик должен существовать в реестре. Его идентификатор — ИНН, а не название компании.
- Счёт из документа должен совпадать с подтверждённым банковским счётом поставщика.
- PostgreSQL — основной источник данных о поставщиках и счетах. Уникальность счёта задаётся парой `supplier_inn + invoice_number`.
- При сравнении проверяются **сумма, валюта, НДС, дата счёта и банковский счёт**. Изменения этих полей приводят к обновлению и увеличению версии.
- Дубль без изменений не создаёт новую запись и не обновляет существующую.
- `bitrix_item_id` хранится в PostgreSQL, чтобы подворкфлоу обновлял существующую карточку вместо создания дубля.

## Данные PostgreSQL

Отдельного DDL / SQL-файла схемы в исходном репозитории нет. Ниже перечислены поля, наблюдаемые в запросах workflow; это описание, а не миграция базы.

| Таблица     | Используемые данные                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `suppliers` | Поиск по `supplier_inn`, подтверждённый `bank_account`                                                                                                                     |
| `invoices`  | `invoice_number`, `invoice_date`, `supplier_name`, `supplier_inn`, `amount`, `currency`, `vat_amount`, `bank_account`, `status`, `version`, `updated_at`, `bitrix_item_id` |

Для `invoices` SQL использует `ON CONFLICT (supplier_inn, invoice_number)`. Существующая запись обновляется только при изменении бизнес-данных.

## Подворкфлоу синхронизации

Подворкфлоу создаёт или обновляет карточку Bitrix24, используя сохранённый `bitrix_item_id`. Для временных ошибок обновления включён Retry On Fail; число попыток задаётся в настройках ноды.

## Справочная последовательность импорта

Этот раздел сохраняет инструкции для отдельного развёртывания n8n. Для работы демосайта эти шаги не нужны и при его публикации не выполняются.

1. Импортировать [подворкфлоу](../bitrix24-sync-subworkflow.json) в изолированное окружение n8n.
2. Настроить в нём PostgreSQL и Bitrix24 OAuth2 credentials; заменить `YOUR_BITRIX24_PORTAL` в двух HTTP Request нодах.
3. Импортировать [основной workflow](../invoice-processing-workflow.json).
4. Настроить Gmail, OpenAI, PostgreSQL и Telegram credentials; заменить `YOUR_TELEGRAM_CHAT_ID` в Telegram-нодах.
5. Выбрать подворкфлоу в двух Execute Workflow нодах, сохранив вызовы после создания и обновления.
6. До активации отдельно проверить бизнес-сценарии и побочные эффекты интеграций на тестовых данных.

Credentials и доступ к рабочим сервисам не входят в публичный репозиторий. Существующий Gmail-trigger workflow не является HTTP API для сайта; будущему подключению посвящён [контракт API](api-contract.md).

## Сценарии проверки отдельного n8n-окружения

| Ситуация                                          | Ожидаемое поведение                                          |
| ------------------------------------------------- | ------------------------------------------------------------ |
| Новый корректный счёт                             | Создание в PostgreSQL, синхронизация с Bitrix24, уведомление |
| Дубль без изменений                               | Завершение без записи, обновления и уведомления              |
| Изменённый счёт                                   | Обновление той же записи, увеличение версии, синхронизация   |
| Неизвестный поставщик                             | Остановка и ручная проверка                                  |
| Несовпадение банковского счёта                    | Остановка до поиска существующего счёта                      |
| Нет обязательных данных или сумма не положительна | Остановка и ручная проверка                                  |
| Временная ошибка обновления Bitrix24              | Повторные попытки по настройкам ноды                         |

Это перечень для проверки отдельно настроенного workflow. Автоматические тесты frontend проверяют только демосценарии, интерфейс и API-адаптер с заглушками.

Возможные дальнейшие улучшения: OCR для сканированных счетов, аудит действий, мониторинг и оповещение о технических ошибках. Согласование счетов в текущий проект не входит.
