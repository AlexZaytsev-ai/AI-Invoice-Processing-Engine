# Контракт будущего backend

Текущая версия автономна. Этот документ описывает подготовленную границу интеграции, а не подключённый сервис. Все тесты backend используют заглушки `fetch`; реальные запросы в n8n и другие сервисы не выполняются.

## Запрос

`POST /api/invoices/process` на том же origin, что и интерфейс.

- Тело: `multipart/form-data`, одно поле `file` с PDF до 10 МБ. `Content-Type` с boundary выставляет браузер.
- Запуск: только явное нажатие кнопки в режиме `VITE_API_MODE=backend`.
- Таймаут ожидания: 60 секунд. При таймауте результат считается неизвестным. Адаптер не повторяет запрос автоматически.
- Авторизация: только механизм backend; frontend не хранит секреты n8n. Для backend на том же origin браузер передаёт его обычные same-origin cookies. Backend отвечает за защиту входной точки.
- Backend обязан заново проверить документ, размер, тип и содержимое. Проверка сигнатуры в браузере — только ранняя подсказка, а не полная проверка PDF.
- Backend должен ограничивать повторную обработку по существующим правилам `supplier_inn + invoice_number`. Отмена ожидания в браузере не гарантирует отмену уже начатой обработки на сервере.
- Автоматические повторы отсутствуют, перенаправления отклоняются. Прямой внешний URL в `VITE_API_BASE_URL` отклоняется.

## Успешный ответ

`200 application/json`, тип `ProcessingResult` из `src/domain/types.ts`. Поля из оригинальной схемы AI-извлечения сохранены в `snake_case`; отсутствующие значения представлены `null`, а не выдуманными значениями.

```json
{
  "contract_version": 1,
  "source": "backend",
  "status": "processed",
  "action": "created",
  "invoice": {
    "document_type": "invoice",
    "invoice_number": "СЧ-1042",
    "invoice_date": "2026-10-14",
    "supplier_name": "ООО «Северные системы»",
    "supplier_inn": "7701234560",
    "amount": 128400,
    "currency": "RUB",
    "vat_amount": 21400,
    "bank_account": "40702810900000001234",
    "payment_due_date": "2026-10-28",
    "missing_fields": []
  },
  "checks": [
    { "id": "required", "status": "passed", "title": "Обязательные данные", "detail": "Номер, ИНН и счёт заполнены. Сумма больше нуля." },
    { "id": "supplier", "status": "passed", "title": "Поставщик в реестре", "detail": "Поставщик найден по ИНН." },
    { "id": "bank", "status": "passed", "title": "Банковские реквизиты", "detail": "Счёт совпадает с подтверждённым." },
    { "id": "duplicate", "status": "passed", "title": "Дубли и изменения", "detail": "Счёт с таким номером и ИНН не найден." }
  ],
  "storage": {
    "record_id": "invoice-1042",
    "version": 1,
    "previous_version": null,
    "created": true,
    "updated": false
  },
  "previous_invoice": null,
  "expected_bank_account": "40702810900000001234"
}
```

Это вымышленный пример. `record_id` — строковый идентификатор записи backend, не обязательно числовой primary key базы.

| Ветка | status | action | storage |
| --- | --- | --- | --- |
| Создание | `processed` | `created` | `created: true`, `updated: false`, версия 1, `previous_version: null` |
| Дубль | `processed` | `duplicate` | оба флага `false`, тот же ID, `version === previous_version` |
| Обновление | `processed` | `updated` | `created: false`, `updated: true`, тот же ID, `version === previous_version + 1` |
| Ручная проверка | `manual_review` | `blocked` | оба флага `false`, `record_id`, `version`, `previous_version`: `null` |

Для обновления `previous_invoice` содержит прежние данные, чтобы показать разницу. Для дубля можно вернуть прежние данные или `null`. Для прочих веток используйте `null`.

`checks` всегда содержит четыре уникальные проверки `required`, `supplier`, `bank`, `duplicate`, в порядке выполнения. Статусы: `passed`, `warning`, `skipped`. После остановки оставшиеся проверки имеют статус `skipped`. При несовпадении реквизитов `bank` имеет статус `warning`, `duplicate` — `skipped`, а `expected_bank_account` содержит подтверждённый счёт. Если реквизиты ещё не проверялись, `expected_bank_account: null`.

Валюта — код из трёх заглавных латинских букв или `null`. Даты — `YYYY-MM-DD` или `null`. Суммы — конечные JSON-числа или `null`. `missing_fields` — массив строк. Результат с неизвестной версией контракта, пропущенными полями или противоречивым статусом отвергается адаптером и не отображается как успешный.

## Ошибки

Валидационное бизнес-решение «ручная проверка» возвращается через `200` с `manual_review`, а не как техническая ошибка. При технической ошибке backend возвращает неуспешный HTTP-статус:

| HTTP | Сообщение интерфейса |
| --- | --- |
| 413 | Файл слишком большой |
| 415 | Формат не поддерживается |
| 422 | Не удалось извлечь данные |
| 429 | Сервис занят |
| Другой неуспешный статус | Backend не смог обработать документ |

Произвольный текст ошибки сервера не выводится в интерфейс: в нём могут быть внутренние адреса или диагностические данные.

## Порядок будущего подключения

1. Создать отдельный backend / reverse proxy и отдельную HTTP-точку входа n8n в изолированном окружении. Исходный workflow запускается через Gmail и не возвращает этот контракт веб-клиенту. Сам по себе этот frontend не превращает его в HTTP API.
2. Спроектировать HTTP-вход и нормализацию ответов, сохранив существующие бизнес-проверки. Учесть, что исходная ветка дубля заканчивается без записи и уведомления: для UI нужен явный результат `duplicate`.
3. Оставить оба имеющихся вызова Sync Invoice to Bitrix24 и оригинальные экспорты неизменными. Решения о внешних интеграциях принимать отдельно от этого демоинтерфейса; здесь их подключение не выполнялось.
4. Хранить webhook URL, credentials и доступ к PostgreSQL только на сервере. Ни одного секрета в `VITE_*`.
5. Настроить same-origin маршрут `/api/invoices/process`. Локальный Vite сейчас никуда не проксирует запросы.
6. Проверить контракт и побочные эффекты backend отдельно, затем явно включить `VITE_API_MODE=backend` и перезапустить / пересобрать frontend. Для возврата к автономности — `VITE_API_MODE=demo`.

Смена режима не проверяет доступность сервера автоматически. До реализации backend режим `backend` включать не нужно.
